01 / Foundations & ownership

Foundations & ownership

Eight world foundations plus Mission: the first-class domain abstraction for intent and progress. Storage engines, models and tracing tools implement these responsibilities.

01Worldone authoritative shared state

The world owns committed entities, components, relationships, missions and executions. Observed facts remain distinct from mission intent. Every client reads an authorized view of the same state; no model owns a parallel world. Storage and synchronization implement this responsibility without defining its meaning.

one world · many readers · explicit writers
02Entityidentity independent of labels and trackers

An entity identifies a robot, object or other thing across observations. A new classification does not rename it. Association uses evidence to connect producer-scoped tracks to stable identities; matching labels alone are not enough.

backpack-A remains the same entity as its measurements change
03Componenttyped state with evidence and time

Components describe facets such as pose, geometry, semantics and robot control. Each observed facet retains its acquisition time, version and provenance. Missing values stay unknown; a label update cannot make stale geometry fresh.

entity + independently timed facets
04Relationshipa directed fact between entities

Relationships connect existing entities using a defined predicate. Observed relationships retain evidence; configured facts remain distinguishable. Removal must preserve reference integrity, rather than leaving dangling endpoints.

subject + predicate + object
05Affordancewhat an actor could do in the current situation

An affordance evaluates an action's requirements against current evidence at a known time. It is a useful read-only hint, not permission to execute. The action boundary repeats freshness, identity and policy checks when accepting a request.

actor + target + requirements → availability and reasons
06Actionintent with bounded execution and a measured outcome

An action names an operation with typed inputs, requirements and an installed implementation. Each request has one stable execution identity. Simulation and physical bindings share intent; hardware additionally enforces local limits, stop and durable receipts. A sent command is not a successful outcome.

intent → admission → execution → evidence
07Systema worker that observes, derives or acts

Perception, association, planners and control adapters have explicit responsibilities. Client workers subscribe to relevant state and changes, then prepare context at their own pace. Inference and physical IO stay outside atomic world writes. Interfaces do not require one microservice per worker.

subscribe to the world · prepare context · propose validated changes
08Eventa recorded occurrence, not just the latest value

Events preserve important transitions and outcomes that current state alone may hide. Clients retain must-handle events until acknowledged. World audit, client attention and diagnostic traces have different retention needs; an update callback is not durable history. Full scene replay needs a separately specified recorder.

current state ≠ important transitions ≠ diagnostic traces
09Missiondurable intent, objectives and evidence-backed progress

A first-class domain abstraction built on the eight world foundations. A mission binds an authorized goal to typed objectives, dependencies and limits. Its state belongs to the shared world, not a model conversation. Clients subscribe and propose actions; validated evidence credits objectives, and physical closure gates the terminal outcome.

mission → ready objectives → executions → evidence → progress
02 / Objects & world view

Objects & world view

Typed geometry, independently timed evidence, a narrow action contract and a read-only world projection.

01Geometry & sensor referencesnative SDK algebraic types

02b / Missions & objectives

Missions & objectives

A mission states what should be achieved and what proves it. Clients choose how to advance it; the world owns its specification, progress and lifecycle.

01Definition & instanceimmutable intent; durable progress

A Mission is an accepted objective graph, its owner, constraints and lifecycle. It survives client restarts and model changes. Keep the bound specification in the mission row; an optional template pin records authoring provenance. No template catalog is needed until reuse warrants one. Resolve entities and authorize the complete specification before activation. A changed goal or a repeat starts a new mission ID; a planner may change its strategy without changing the agreed outcome.

author / resolve → authorize specification → active mission
02Objectives & dependenciesoutcome graph, not a fixed action script

Each objective has a stable ID, a typed criterion and an all-of dependency list. Independent objectives can progress in parallel. Optional objectives do not block completion and cannot be prerequisites of required ones. Reject duplicate IDs, missing references, cycles, empty required sets and graphs above 32 nodes. These are milestones: acquiring geometry once does not mean it stays fresh forever. Continuous conditions remain action admission and local-control checks.

geometry + semantics → approach → fresh geometry
03Evidence-backed creditone durable proof per objective

The first slice supports acquiring a geometry/semantic facet for a bound entity and completing approach@1 for exact participants and standoff. The reducer loads the retained observation or execution itself. It checks authorization, source association, objective readiness and evidence time; an LLM cannot submit a success boolean or increment a counter. One immutable credit per mission/objective makes redelivery harmless. Readiness begins at activation or the latest prerequisite credit. Observations must be acquired after readiness and still meet maxAgeMs; executions must be admitted after readiness and carry the matching mission link. Retain referenced evidence with the credit.

domain proof → validated credit → derived ready/completed objectives
04Lifecycle & safe closureactive → closing → terminal

Creation activates an authorized, fully bound specification. All required credits request success; cancellation requests cancellation; a deadline requests failure. Closing blocks new admission and claim, requests cancellation of unfinished linked attempts and waits for confirmed safe closure. Terminal failure with an unknown physical outcome is not safe closure. Cancellation may replace pending success until terminal commit; once terminal, the mission is immutable. A deadline reached during closing also prevents success. A failed action does not automatically fail the mission: a fresh attempt is possible while active, but first reconcile the old attempt.

goal achieved ≠ all physical work safely closed
05Mission subscriptions & authorityshared mission; independent decision clients

Clients subscribe to mission state, credits, relevant world evidence and linked executions. Prepare context from that shared mission plus the ready objectives. Mission and objective pins travel with action requests; admission and claim recheck readiness, deadline, owner authority, exact criterion and the tighter mission/installed limits. The first slice permits owner or administrator mutations, not implicit delegation to every subscriber. An action's missing mission link is allowed only on an explicit standalone operator path, never as a way around mission cancellation.

mission + relevant world → subscription → context → proposal
06Small first sliceborrow the pattern, not an MMO engine

Use one mission table and one immutable credit table; derive objective progress instead of storing another mutable counter. Repeated sensor frames do not count as distinct objects. Add counted objectives only with an explicit distinct-item identity and deduplication rule. Dynamic branches, nested missions, pause/resume, shared-party permissions, rewards, reset calendars and automatic quest chains are deferred. Add a new typed criterion and validator when a concrete mission needs it; unsupported goals need clarification, not a generic JSON escape hatch.

two tables · one mission boundary · existing execution protocol
07MMO referencespatterns borrowed and adapted
Definition vs progress
AzerothCore quest definitions and character quest status separate reusable content from a participant's progress. Nemeia adopts that distinction, with an inline immutable specification per mission.
Objective composition
EQEmu task activities define typed goals, counts, optional activities and ordered steps. Nemeia uses typed milestones and explicit dependencies, keeping the first slice smaller than a general workflow engine.
Typed objective records
TrinityCore's QuestObjective separates objective identity, type, target and amount. Nemeia follows the typed-objective pattern but replaces gameplay credit with validated domain evidence.

These are primary references for open-source MMO server implementations, not claims about Blizzard's or Daybreak's internal databases. The Nemeia adaptation below is a design decision, not an MMO standard.

01ObjectiveSpec & criteriontyped milestone and all-of dependencies

Only two validators are specified initially. An observed semantic facet proves that hypotheses were acquired, not that the hypothesis is true. An approached criterion requires a measured successful receipt, not merely a command.

export const ObjectiveCriterion = t.enum("ObjectiveCriterion", {
  observed: t.object("ObservedCriterion", {
    entityId: t.string(), // bound existing entity; a label is not an identity
    facet: t.enum("ObservedFacet", ["geometry", "semantic"]), // requires this measured/derived facet, not proof its label is true
    maxAgeMs: t.u32(), // positive maximum acquisition age when credit is granted
  }),
  approached: t.object("ApproachedCriterion", {
    actorId: t.string(), targetId: t.string(), // exact installed approach@1 participants
    standoffM: t.f64(), // exact requested goal; success uses the binding's measured tolerance
  }),
}); // first slice: two installed validators; no arbitrary expression language or model-written success code
export const ObjectiveSpec = t.object("ObjectiveSpec", {
  id: t.string(), // unique within the immutable mission specification
  description: t.string(), // explanation only; the criterion determines credit
  dependsOn: t.array(t.string()), // all named objectives must be credited first; no cycles
  optional: t.bool(), // excluded from mission completion; cannot gate a required objective
  criterion: ObjectiveCriterion, // a milestone supported by retained domain evidence
});
export type ObjectiveSpec = Infer<typeof ObjectiveSpec>;
02MissionSpec & lifecycleaccepted intent and constraints

The SDK builders define the storage types; runtime validation still has to enforce finite limits, bounded graphs, actor permissions and reference integrity. A mission is a first-class domain object built on the existing world foundations.

03 / Service contracts

Service contracts

Each boundary has one owner. These interfaces specify behavior, not separate microservices. The selected database binding implements world writes as reducers.

01Missionsaccepted specification → verified progress → safe closure

Owner/admin operations. Validate bounded acyclic graphs, live bound entities, actor permissions, positive finite limits and future deadlines. Credits load retained proof and validate readiness; they never trust client counters. Reconciliation is idempotent and scheduled for deadlines even without sensor writes. Mission reducers and authorized views remain implementation work.

export interface Missions {
  createMission(input: { id: string; spec: MissionSpec }): Promise<void>; // owner from identity; validate bound graph, limits and deadline; atomically activate + audit
  creditObjective(input: { missionId: string; objectiveId: string; evidence: MissionEvidence }): Promise<void>; // validate proof/readiness; atomically credit + audit and enter closing if all required objectives are met
  cancelMission(input: { missionId: string; expectedRevision: bigint }): Promise<void>; // idempotent if cancellation already requested; otherwise compare revision, block new work and cancel linked attempts
  reconcileMission(input: { missionId: string }): Promise<void>; // enforce deadline/completion; close only after all linked attempts have confirmed safe closure
} // owner/admin calls; no setProgress(), arbitrary success flag or model-controlled completion
02PerceptionIngressobservations → association and current components

Authorize producer identity, package/session and owned facets. Compare identical retry bodies before assigning identities. Validate clock error, transforms, endpoints, supersedes references and monotonic facet times. Commit observation, track binding, supplied component changes and audit together.

export interface PerceptionIngress {
  ingestObservation(input: ObservationInput): Promise<void>; // authorize producer; associate; atomically update supplied facets + audit
} // identical ID + principal + input retries are no-ops; changed duplicates conflict
03ActionRequestsa valid request becomes one accepted execution

Check the existing execution ID first: same caller and immutable body is a retry, even after the deadline; a changed request conflicts. For new IDs, check active mission/revision, ready matching objective, owner permissions and mission deadline/limits, then live actor/target, binding, stop projection, fresh evidence and geometry pin. Atomically reject a second nonterminal attempt for the same mission/objective. No model probability bypasses these checks.

export interface ActionRequests {
  requestApproach(input: ApproachRequest): Promise<void>; // validate policy and evidence; insert one accepted execution + audit
} // duplicate same caller/body returns the existing receipt even after acceptBy; it does not run again
04ExecutionClaimsreserve one robot before physical IO

Only the bound controller can claim. In one transaction, recheck active mission/revision, objective readiness, deadline, fresh evidence and target pin, reserve the actor and set running. Use the acceptance deadline as the claim deadline too. A late accepted request cannot start. An identical existing claim remains reconcilable after expiry, but reconciliation is not permission to restart cancelled physical work.

export interface ExecutionClaims {
  claimExecution(input: {
    executionId: string; // accepted attempt, or an identical claim retry by this controller
    controllerEpoch: bigint; // must match robot_control AND the local controller's persisted generation
  }): Promise<void>; // recheck pins/freshness; reserve actor and set running in the same transaction
} // do not steal a running attempt on timeout; a database fence alone cannot stop a physical robot
05Cancellationrequest safe closure, not instant physical stop

Cancellation is idempotent and belongs to the requesting operator or admin. Set cancelling and record the request atomically. The local controller confirms safe closure before a terminal cancellation. Cancelling an unclaimed attempt requires the controller to confirm it never started; expiry alone is not proof.

export interface Cancellation {
  cancelExecution(input: { executionId: string }): Promise<void>; // transition accepted/running to cancelling; never imply physical stop
} // local controller confirms safe state before cancellation becomes terminal
06ControlFeedbackproject measured controller state

Only the enrolled controller and current epoch can report. Reject stale/future reports. A remote false stopLatched value never clears the actual local latch. Keep actor reservations if safe state is unknown.

export interface ControlFeedback {
  reportControl(input: {
    actorId: string; controllerEpoch: bigint; // authenticated robot owner and current fence
    observedAt: Timestamp; // control acquisition time, not report arrival time
    stopLatched: boolean; safeStateConfirmed: boolean; // measured local state; uncertainty stays explicit
  }): Promise<void>; // update robot_control; cannot claim, clear a local latch or authorize motion
}
07ExecutionCompletionmeasured outcome → immutable terminal receipt

Verify controller ownership, epoch, actor/target measurement identities and freshness, applicable target-motion policy, requested tolerance and the local safe-closure receipt. Cancellation wins once cancelling is committed. A failed outcome with unknown safe state retains the robot reservation until reconciliation.

export interface ExecutionCompletion {
  finishExecution(input: {
    executionId: string; controllerEpoch: bigint; // same claimed attempt and controller generation
    result: Completion; // success includes measurement IDs and a durable safe-closure receipt
  }): Promise<void>; // validate outcome, commit terminal state + audit, release the active actor only if safe
} // if cancelling committed first, reject success; reconcile cancellation or failure instead
08WorldAdministrationexplicit provisioning and lifecycle

Restrict enrollment and binding installation to administrators. Reducers enforce relationship integrity; there is no assumed SQL foreign-key cascade. Refuse entity removal while active executions depend on it. New control generations require a verified local stop and persisted local fence, not just an incremented database counter.

export interface WorldAdministration {
  putMember(input: Row<"member">): Promise<void>; // admin-only enrollment; bound role, robot and producer package
  installApproach(input: Row<"actionBinding">): Promise<void>; // admin-only installation; increment version; never mutate an active pin
  removeEntity(input: { entityId: string }): Promise<void>; // reject active references; tombstone and remove components/relations atomically
  reconcileController(input: { actorId: string; newController: Identity; newEpoch: bigint; receiptId: string }): Promise<void>; // only after local safe stop and fence installation are verified
} // provisioning establishes the first admin out of band; never expose an unauthenticated bootstrap reducer
09LocalControllerrobot-local durability, limits and stop

This boundary stays outside SpacetimeDB. Use an existing navigation stack/driver, OS supervision, local persistent receipts and a monotonic watchdog. After a crash, reconcile receipts before delivery. Do not time out and reassign a physical attempt while an old worker may still be acting.

export interface LocalController {
  reconcile(executionId: string): Promise<LocalReceipt | undefined>; // inspect persistent outcome before considering any delivery
  start(input: {
    executionId: string; controllerEpoch: bigint; // immutable idempotency key plus installed local fence
    request: ApproachRequest; binding: Row<"actionBinding">; // exact accepted intent and tighter local limits
  }): Promise<LocalReceipt>; // persist before IO, reject changed duplicates, then bounded local navigation
  cancel(executionId: string): Promise<LocalReceipt>; // enter safe state locally; works without the world database
  stop(reason: string): Promise<LocalReceipt>; // latch stop locally first; do not depend on a subscription or cloud call
}
export interface LocalReceipt {
  id: string; executionId: string; controllerEpoch: bigint; // stable receipt identity and attempt correlation
  outcome: "notStarted" | "running" | "succeeded" | "cancelled" | "failed" | "unknown"; // sent is never succeeded
  safeState: "confirmed" | "unknown"; // uncertainty blocks new physical attempts
} // robot-local durable storage, not an extra remote table; independent monotonic watchdog and OS supervision
10EvidenceStorageretained bytes stay off the state path

Media continues over the appropriate streaming transport. Retained images, masks, clouds and meshes use existing blob storage. Only validated immutable references enter the world; credentials and expiring download URLs do not become component values.

export interface EvidenceStorage {
  resolve(resourceId: string): Promise<{ url: string; expiresAt: Timestamp }>; // authenticated access to retained bytes; explicit missing/expired result
} // existing blob storage and media transport; no image/cloud byte arrays in live component tables

05 / Implementation choices

Implementation choices

Concrete tools underneath the model. These are implementation targets, not live integrations or new foundational abstractions.

01World storage · SpacetimeDBselected implementation, not a Nemeia primitive

Typed tables persist the shared world. Reducers validate atomic changes; authorized subscriptions maintain consistent read caches. The SDK examples below show this binding. Nemeia's entities, evidence, actions and ownership rules define the model; adopting another backend would still have to preserve those guarantees.

World → tables · writes → reducers · readers → subscriptions
02Perception & decisions · specialized workerschoose tools by task and cadence

YOLOE handles frequent detection, with SAM3 available for selective refinement. Spatial/audio workers produce structured evidence. Typesafe, LLMs and rules consume prepared context; none owns a separate world or bypasses admission. These integrations are specified, not connected by this page.

one observation boundary · one action boundary
03Diagnostics · Laminar + OpenTelemetryinspect application content as well as timing

Capture approved step context, prompts, responses, selected evidence and tool results in Laminar. OpenTelemetry supplies span structure and propagation. Exclude credentials, bound retention and restrict access; sensitive application content is not automatically forbidden. Export stays outside the control path.

context + evidence + decisions + outcomes → diagnostic traces

02Native reducer · cancel_executionatomic lifecycle change and audit

This concrete SDK example shows a real transaction boundary. It records cancellation intent, not a claim that hardware has stopped. The other reducer behaviors are design contracts to implement.

export const cancel_execution = db.reducer(
  { executionId: t.string() }, // caller identity comes from ctx.sender, not this input
  (ctx, { executionId }) => {
    const caller = ctx.db.member.identity.find(ctx.sender);
    const row = ctx.db.execution.id.find(executionId);
    if (!caller || !row) throw new Error("not_found_or_forbidden");
    const owns = row.requestedBy.isEqual(ctx.sender);
    if (caller.role.tag !== "admin" && !(caller.role.tag === "operator" && owns)) {
      throw new Error("forbidden");
    }
    if (row.state.tag !== "accepted" && row.state.tag !== "running") return; // idempotent; terminal states stay immutable
    ctx.db.execution.id.update({ ...row, state: { tag: "cancelling" }, updatedAt: ctx.timestamp });
    ctx.db.worldEvent.insert({
      sequence: 0n, id: ctx.newUuidV4().toString(), // autoInc assigns the audit sequence
      kind: "execution.cancel_requested", subjectId: row.id, actor: ctx.sender,
      recordedAt: ctx.timestamp, detail: "Await local safe-state confirmation",
    }); // both writes commit or both roll back
  },
); // returns no domain object; observe the authorized execution view for the resulting row
03Native view · visible_executionsauthorization on the server

Private base tables stay inaccessible to ordinary clients. This public view returns only rows permitted by the authenticated member role. Apply the same membership boundary to world read views and dedicated worker projections; a client-side WHERE filter is not access control.

export const visible_executions = db.view(
  { name: "visible_executions", public: true },
  t.array(execution.rowType), // an identity-scoped view, not a public execution table
  (ctx) => {
    const caller = ctx.db.member.identity.find(ctx.sender);
    if (!caller) return [];
    if (caller.role.tag === "admin" || caller.role.tag === "viewer") return [...ctx.db.execution.iter()];
    if (caller.role.tag === "operator") return [...ctx.db.execution.requestedBy.filter(ctx.sender)];
    if (caller.role.tag === "controller" && caller.robotId !== undefined) {
      return [...ctx.db.execution.actorId.filter(caller.robotId)];
    }
    return []; // perception credentials cannot inspect command history
  },
); // SDK subscriptions receive a consistent initial result and committed changes

06 / Perception & decision systems

Perception & decision systems

Use each tool for its task. Multimodal processing builds a shared world; Typesafe, LLMs and rules consume that world through the same decision and action boundaries.

01YOLOE · frequent perceptiontext / visual prompts → detections and optional masks

Use YOLOE as the first candidate for the local, frequent perception path. Its open-vocabulary detection and segmentation accept text or visual prompts; prompt-free checkpoints are a separate mode. Start with a small checkpoint, a task-scoped class list and a bounded input resolution. Use a tracker between detections. This is a hardware-dependent choice to benchmark, not a promised frame rate.

camera → YOLOE + tracker → PerceptionIngress
02SAM3 · selective refinementambiguous or new targets → richer segmentation

Keep SAM3 available for prompted segmentation and tracking when the fast path cannot resolve a target or needs a better mask. Schedule it on demand or at a lower rate, not as a prerequisite for every frame. Both paths produce the same observations. Neither a detector nor a mask alone supplies measured 3D geometry or stable world identity.

selected frame / region → SAM3 → same observation boundary
03Perception scheduling & identityfresh evidence before throughput

Keep one latest pending frame per stream and bound in-flight inference. Preserve acquisition timestamps and reject obsolete results; dropping queued frames must not make old evidence appear fresh. Tracking predictions are not new measurements. Share association across models; qualify cross-model matches instead of merging by label. Pin checkpoint, prompt profile and runtime in producer provenance. Benchmark end-to-end p95 latency, memory, dropped frames and task accuracy before setting rates. ONNX/TensorRT are optional optimizations; exported prompted classes may be fixed and require re-export when changed.

YOLOE frequent · SAM3 selective · one association owner
04Spatial and audio processingdepth, LiDAR, localization and speech → structured observations

Calibrated depth/LiDAR and acquisition-time transforms supply measured geometry. Association maps tracks to entity identities. ASR supplies a transcript; the authenticated task boundary determines whether speech is an authorized request. Geometry calculations and known numeric checks stay in ordinary code.

mask + calibrated depth + transform → boundingBox3D; audio → transcript
05LLMs and vision-language modelsinterpret unfamiliar inputs; compose and revise plans

A vision-language model may add semantic hypotheses with provenance. An LLM can interpret a goal, compose installed actions, draft focused decision questions and handle unfamiliar situations. Test and version these definitions before activation. Neither a generated description nor a plan changes permissions, invents an executor or overwrites measured state.

goal + installed actions → proposed plan / versioned questions
06Typesafe · bounded semantic decisionsstructured state → choice, score or yes/no probability

Jev reads text/structured state produced by upstream tools. Use Choice for a known candidate set, Score for a defined rubric, and Noul for a yes/no probability. Independent questions can share one request; they do not see each other's answers. Apply the results in code, with abstention and task-tested thresholds. Noul has no separate confidence field.

Which observed entity matches this goal? → candidateA | candidateB | none
07Rules, reducers and local controlexact checks → admitted action → bounded execution

Code checks identity, freshness, geometry, permissions and numeric limits. The world owner repeats those checks when admitting a request. Navigation and robot-local control execute the accepted action and enforce watchdogs and stop. Model outputs remain proposals. API outages or stale predictions cannot authorize motion.

DecisionRecord → ordinary ActionRequest → executor → new evidence

06b / Client subscriptions

Client subscriptions

Subscriptions select what a client follows. Inboxes buffer what needs attention. Context is the frozen input prepared when that client is ready to decide—not a new copy of the world.

01Subscription scopewhich mission and world changes this client follows

Each logical client selects its mission, objective credits and relevant entities, components, relationships and executions from authorized views. Include dependencies needed for its ready objectives, not just a label such as backpack. Clients follow the same mission progress with independent inbox progress; they do not compete for one shared queue. Filters narrow interest, not permissions. Changing scope requires a fresh matching view and review of active-step dependencies. Rows entering or leaving a query are not proof of a physical appearance or disappearance. Use native database subscriptions; no new transport is needed.

mission + authorized world views → subscribed state and changes
02Per-client inboxlatest state plus events that must be handled

Reasoning clients buffer work behind their subscriptions. For replaceable state, keep changed entity keys and read the newest values at the next step. Preserve user messages, tool results and important transitions individually, including messages arriving outside world subscriptions. If an object appeared and disappeared between steps, its latest state is not a substitute for a required appearance event. A display-only client can render its subscribed cache directly; not every subscriber needs a durable inbox.

coalesce state · retain events · never queue every camera update
03Context preparationcompile just before inference begins

Wait until the required subscriptions are ready. At a consistent committed-cache boundary, reserve an exact event batch and detach the relevant world projection. Add the authorized goal, constraints, available actions, current executions and selected conversation/tool history. Preserve missing values, evidence times and relevant versions. Bound tokens and retained bytes; defer excess work without silently dropping must-handle events. Freeze the input and record its context ID before the model starts. After a disconnect, resynchronize and review dependencies before proposing new physical work.

subscribed state + goal + pending events + history → immutable step context
04Scheduling & interruptionan update is not an instruction to infer

Wake on user input, tool completion, meaningful changes or a deadline—not every sensor update. Start with one active reasoning step per logical agent. While inference runs, subscriptions keep the cache current and the inbox collects later work. Never edit an in-flight prompt. A cancelled task or invalidated target supersedes the step; reject late results even if cancellation fails. Physical stop bypasses this scheduler. UI clients render continuously, rules can react promptly, and Typesafe or LLM workers use task-specific cadences.

90 pose updates during one step → one latest pose for the next
05Decisions & feedbacksubscribers propose; execution checks current authority

A client may propose an action, ask for clarification or make no change. Subscription access never grants execution permission. Before acting, review the prepared context against current task dependencies and request admission using fresh evidence. Admission, controller claim and local limits still apply. Execution receipts and measured outcomes return through the same subscriptions and can wake the next step. Wake rules should distinguish relevant outcomes from the client's own bookkeeping writes to avoid a self-triggering loop.

subscribe → prepare → decide → validate → execute → observe
06Durability & acknowledgementhandled means a durable outcome, not read

Persist must-handle events and client progress when restart recovery matters. Reuse retained domain events only when they contain the required occurrence; a subscription reconnect is not replay. Record the step outcome before acknowledging its exact event IDs, leaving newer arrivals pending. Failed or superseded steps retain unhandled events. Delivery retries reuse identities; re-evaluation after release gets a new step ID and must reconcile any prior physical attempt. Bound required-event queues with explicit admission/backpressure; dirty-key overflow can instead trigger a rescan. Worker inbox progress is not mission progress: its store and crash recovery remain separate from the world tables.

reserve batch → persist outcome → acknowledge batch
01ClientSteps & PreparedStepreasoning lifecycle behind a subscription

A worker-local design contract, not a subscription transport or required queue service. A prepare operation reserves events without acknowledging them. Recovery must reconcile the active step and durable outcome before retrying; a trace is not the progress ledger.

09 / Failure & deployment boundaries

Failure & deployment boundaries

A fast shared-state engine does not remove uncertainty, authority checks, network failures or robot-local safety responsibilities.

01Changed context or stale evidencereview intent; recheck the action

A cancelled goal, superseded step or lost target invalidates a proposal. A new pose sample does not automatically invalidate the whole reasoning step: re-evaluate relevant dependencies using explicit task rules, conservatively recomputing when equivalence is unknown. Read fresh evidence for the action request, pin its current geometry version and let admission/claim repeat strict checks. Inference deadlines are not physical evidence-age limits.

reasoning validity ≠ permission to act
02Disconnect, retry or lost acknowledgementreconcile before acting

Reconnect reconstructs current subscribed state, not every missed event. Use the execution row and robot-local receipt to determine what happened. Bound retries and disable offline queuing of new motion requests. Keep confirmed reads enabled for decision consumers.

same execution ID · same immutable request
03Model uncertainty or API outageabstain; remain within local limits

Use explicit none/unknown choices and qualified thresholds. Coalesce relevant changes, bound concurrency and prevent target oscillation. An LLM may propose a new plan, but receives no privileged execution path. Test selection in shadow mode before enabling autonomous requests.

no new autonomous motion from a missing or expired answer
04Capacity and deploymentone nearby world host first

SpacetimeDB's documented tables are memory-resident with durable backing. Keep raw media elsewhere and bound history. Benchmark Nemeia's write fan-out, view cost, recovery, and p95/p99 latency; MMO use is evidence of a useful pattern, not a robotics real-time guarantee. The static Site is documentation, not the database host.

measure the workload before expanding to a fleet
05License and multiple instancescheck deployment rights before fleet rollout

The engine's current BSL additional grant restricts production use to one instance for an application/service, subject to its full terms. A database and an instance are different scopes. Review the selected release and commercial terms before independent robot/customer installations.

source-available engine ≠ unrestricted multi-instance production grant
